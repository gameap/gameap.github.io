Менеджер процессов — компонент GameAP Daemon, через который демон запускает игровые серверы на ноде.
Отвечает за запуск, остановку и перезапуск игровых серверов, за мониторинг их состояния, сбор статистики и ограничение ресурсов (CPU / RAM).

По умолчанию демон выбирает менеджер сам. В Linux используется `systemd`; если сам демон работает внутри контейнера,
либо `systemctl` отсутствует, либо systemd не является процессом с PID 1, демон переключается на `tmux`, а если tmux
тоже не установлен — на `simple`. В Windows по умолчанию используется [Shawl](https://github.com/mtkennerly/shawl),
в macOS — `tmux`.

## Конфигурация

Менеджер процессов настраивается в блоке `process_manager` [файла конфигурации GameAP Daemon](/ru/daemon/daemon.html).
При добавлении ноды через панель менеджер можно выбрать заранее: разверните блок **Дополнительные настройки** и укажите
его в поле **Менеджер процессов**. На вкладке Linux доступны **Авто (Рекомендуется)**, **Простой (Управление скриптами)**,
SystemD, Docker, Podman и Tmux; на вкладке Windows — только **Авто (Рекомендуется)**, **Простой (Управление скриптами)**,
WinSW и Shawl, поэтому Docker в Windows нужно прописывать в файле конфигурации вручную.

### Базовая структура

```yaml
process_manager:
  name: <имя_менеджера>
  config:
    <ключ>: <значение>
```

**Доступные менеджеры:**
- Linux: `systemd` (по умолчанию), `docker`, `podman`, `tmux`, `simple`
- macOS: `tmux` (по умолчанию), `docker`, `podman`, `simple`
- Windows: `shawl` (по умолчанию), `winsw`, `simple`, `docker` (Podman в Windows не поддерживается)

Содержимое `config` зависит от менеджера:

| Менеджер                           | Ключи в `config`                                                                                                                  |
|------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------|
| `systemd`                          | `scope` — `system` или `user`, см. [Конфигурация Systemd](#конфигурация-systemd)                                                  |
| `docker`                           | `host`, `cert_path`, `api_version`, а также любой [параметр контейнера](#параметры-контейнера) как значение по умолчанию для ноды |
| `podman`                           | `socket_path`, а также любой [параметр контейнера](#параметры-контейнера) как значение по умолчанию для ноды                      |
| `tmux`, `simple`, `shawl`, `winsw` | нет                                                                                                                               |

> Ключ `scope` принимает только `systemd`. С любым другим менеджером демон не запустится и выдаст ошибку
> `process_manager.config.scope is only valid for process_manager.name=systemd`.

### Перезапуск после сбоя

Кто поднимает упавший игровой сервер, зависит от менеджера. У `systemd` это делает сам unit (`Restart=always`), у Shawl —
служба (`--restart`), у WinSW — действия `onfailure` службы. С `tmux`, `simple`, Docker и Podman сервер перезапускает сам
демон: раз в 5 секунд он проверяет состояние всех серверов и запускает те, что не работают. Давно простаивающие серверы
демон опрашивает реже, поэтому такой перезапуск может задержаться примерно на две минуты. Во всех случаях учитывается
настройка сервера **«Автозапуск в случае падения»**: сервер, остановленный намеренно, повторно не запускается.

### Статистика

`systemd`, Docker и Podman отдают полный набор метрик: CPU, использование и лимит памяти, сетевой трафик, дисковый
ввод-вывод и число процессов. `tmux`, `simple`, Shawl и WinSW сообщают только, запущен ли сервер. Сбор метрик описан на
странице [GameAP Daemon](/ru/daemon/daemon.html#сбор-метрик).

## Linux и macOS

### Systemd

Платформы: Linux.

Используется по умолчанию в Linux. Это современный менеджер процессов, который обеспечивает высокую производительность и надежность.
Изоляция для этого менеджера процессов имеет ограниченные возможности.

| Функционал                             |                               |
|----------------------------------------|-------------------------------|
| Запуск, остановка, перезапуск серверов | ✅                            |
| Перезапуск после сбоя                  | ✅ Сам unit, `Restart=always` |
| Статистика                             | ✅                            |
| Ограничение ресурсов (CPU / RAM)       | ✅                            |
| Чтение консоли                         | ✅                            |
| Отправка команд в консоль              | ✅                            |
| Изоляция                               | ⚠️ Ограниченная               |

> Unit-файлы, созданные до того, как демон начал записывать в них директивы `CPUAccounting=yes`, `MemoryAccounting=yes`,
> `IOAccounting=yes`, `IPAccounting=yes` и `TasksAccounting=yes`, отдают нулевую статистику, пока сервер не будет
> перезапущен и unit-файл не будет пересоздан.

#### Конфигурация Systemd

Systemd не требует дополнительной конфигурации. Daemon автоматически создаёт и управляет unit-файлами.
Единственный параметр — `scope`:

| Ключ в config | Описание                                                                  | По умолчанию |
|---------------|---------------------------------------------------------------------------|--------------|
| `scope`       | Где размещаются unit-файлы и от кого они запускаются: `system` или `user` | `system`     |

* `system` — unit-файлы записываются в `/etc/systemd/system`; демону нужны права на управление системными unit-ами
  (обычно он работает от root). В каждый unit записываются `User=` / `Group=` из пользователя игрового сервера (поле
  **«Имя пользователя на выделенном сервере»**), поэтому серверы на одной ноде могут работать от разных пользователей.
* `user` — unit-файлы записываются в `~/.config/systemd/user/` и управляются через `systemctl --user`. Демон работает от
  обычного пользователя, и **все игровые серверы работают от этого же пользователя**. Для него должен быть включён
  linger (`sudo loginctl enable-linger <пользователь>`), иначе демон предупредит, что пользовательские службы будут
  завершены при выходе из сеанса; должен быть доступен `XDG_RUNTIME_DIR` (обычно `/run/user/<uid>`). Сервер, у которого в
  поле **«Имя пользователя на выделенном сервере»** указан другой пользователь, не запустится с ошибкой
  `server requests user "..." but daemon runs as "..."`.

##### Примеры конфигурации

По умолчанию (системный scope):
```yaml
process_manager:
  name: systemd
```

Пользовательский scope:
```yaml
process_manager:
  name: systemd
  config:
    scope: user
```

### Docker

Платформы: Linux, macOS, Windows.

Docker запускает каждый игровой сервер в отдельном контейнере, изолируя его от ноды и от других серверов.

> Для игр, импортированных из egg Pelican или Pterodactyl, Docker или Podman **обязателен**. У импортированного egg нет
> правил установки GameAP: его файлы устанавливает скрипт, который выполняется в собственном образе контейнера из egg
> (`docker_installation_image` + `docker_installation_script`). С `systemd`, `tmux`, `simple`, `shawl` или `winsw` такой
> сервер установить нельзя — установка завершается ошибкой `could not determine the rules for installing the game`.
> См. [Импорт игр](/ru/gameap_configure/games_import.html#особенности-pelican-и-pterodactyl).

| Функционал                             |                  |
|----------------------------------------|------------------|
| Запуск, остановка, перезапуск серверов | ✅               |
| Перезапуск после сбоя                  | ✅ GameAP Daemon |
| Статистика                             | ✅               |
| Ограничение ресурсов (CPU / RAM)       | ✅               |
| Чтение консоли                         | ✅               |
| Отправка команд в консоль              | ✅               |
| Изоляция                               | ✅               |

#### Конфигурация Docker

##### Параметры подключения

| Ключ в config | Описание                                                                              | По умолчанию |
|---------------|---------------------------------------------------------------------------------------|--------------|
| `host`        | Адрес Docker-демона, например `unix:///var/run/docker.sock` или `tcp://10.0.0.5:2376` | —            |
| `cert_path`   | Каталог с `ca.pem`, `cert.pem` и `key.pem` для подключения по TLS                     | —            |
| `api_version` | Версия Docker API                                                                     | —            |

Если ни один из трёх ключей не задан, подключение настраивается из стандартных переменных окружения Docker
(`DOCKER_HOST`, `DOCKER_CERT_PATH`, `DOCKER_TLS_VERIFY`, `DOCKER_API_VERSION`) — без них используется локальный
Docker-демон.

Любой [параметр контейнера](#параметры-контейнера) тоже можно указать в `config` как значение по умолчанию для всей
ноды, с префиксом `docker_` или без него (`image` и `docker_image` равнозначны). Не задавайте `container_name` для всей
ноды: все серверы на ней получат одно и то же имя контейнера.

##### Примеры конфигурации

Минимальная:
```yaml
process_manager:
  name: docker
```

Удалённый Docker-демон по TLS:
```yaml
process_manager:
  name: docker
  config:
    host: tcp://10.0.0.5:2376
    cert_path: /etc/gameap-daemon/docker-certs
```

Параметры контейнеров по умолчанию для ноды:
```yaml
process_manager:
  name: docker
  config:
    image: docker.io/gameap/debian:latest
    workdir: /server
    dns: 8.8.8.8,1.1.1.1
```

#### Параметры контейнера

Docker и Podman читают настройки контейнера из одних и тех же ключей (у Podman они сохраняют префикс `docker_`). Ключи
задаются в панели как метаданные: в разделе **Администрирование → Игры** вкладка **Метаданные** есть и в форме игры, и в
форме модификации. Кнопка **?** рядом с полем ключа открывает справочник **Ключи метаданных** с описанием и примером для
каждого ключа и вставляет выбранный ключ в поле.

| Ключ                             | Описание                                                                                                                                    | По умолчанию              |
|----------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------|---------------------------|
| `docker_image`                   | Образ, в котором запускается игровой сервер. Если тег не указан, добавляется `:latest`                                                      | `docker.io/gameap/debian` |
| `docker_container_name`          | Имя контейнера                                                                                                                              | XID сервера               |
| `docker_workdir`                 | Рабочий каталог внутри контейнера; в него монтируется каталог сервера                                                                       | `/server`                 |
| `docker_network_mode`            | Сетевой режим. Работает только значение `host`, оно включает сеть хоста                                                                     | bridge                    |
| `docker_dns`                     | DNS-серверы контейнера через запятую. Только IP-адреса                                                                                      | —                         |
| `docker_volumes`                 | Дополнительные монтирования вида `источник:цель[:ro]` через запятую или JSON-массивом. Относительный источник считается от каталога сервера | —                         |
| `docker_capabilities`            | Дополнительные Linux capabilities через запятую без пробелов                                                                                | —                         |
| `docker_privileged`              | Привилегированный режим. Включается только точным строковым значением `true`                                                                | —                         |
| `docker_installation_image`      | Образ для этапа установки. Работает только вместе с `docker_installation_script`                                                            | —                         |
| `docker_installation_script`     | Тело скрипта установки. Выполняется в установочном контейнере в `/mnt/server`, куда смонтирован каталог сервера                             | —                         |
| `docker_installation_entrypoint` | Интерпретатор скрипта установки                                                                                                             | shebang, иначе `/bin/sh`  |
| `docker_installation_user`       | Пользователь, от которого выполняется установка                                                                                             | `root`                    |

**Порядок разрешения.** Демон ищет ключ в следующем порядке и берёт первое непустое строковое значение:

1. переменные игрового сервера — значения по умолчанию переменных модификации, затем значения, заданные для самого
   сервера;
2. метаданные модификации;
3. метаданные игры;
4. `process_manager.config` в файле конфигурации демона, где ключ можно записать с префиксом `docker_` или без него.

Используются только строковые значения; число или логическое значение в метаданных игнорируется.

> Блок **Метаданные** самого игрового сервера GameAP Daemon 4.1.2 не читает, хотя справочник панели предлагает там ключи
> контейнера. Чтобы переопределить ключ для одного сервера, добавьте в модификацию переменную с тем же именем (например
> `docker_image`) и задайте её значение в **Настройках** сервера.

> Игры, импортированные из egg Pelican или Pterodactyl, получают в метаданных модификации **Default** ключи
> `docker_image`, `docker_installation_image`, `docker_installation_script`, `docker_installation_entrypoint`,
> `docker_installation_user: root` и `docker_workdir: /home/container`. Кроме них импорт сохраняет `docker_startup_done`
> (маркер завершения запуска из egg) в метаданных модификации и `pelican_egg` (исходный JSON egg) в метаданных игры и
> модификации. Эти два ключа GameAP Daemon не читает — они хранятся для справки.

#### Как это работает

Относится к Docker и Podman в равной мере, если не указано иное.

* Контейнер называется по XID сервера (`docker_container_name` переопределяет имя). Контейнеры, созданные старыми
  версиями демона и названные по UUID сервера, тоже находятся.
* Каталог сервера монтируется в контейнер (bind mount) по пути `docker_workdir` (по умолчанию `/server`), он же является
  рабочим каталогом. Между перезапусками сохраняются только этот каталог и дополнительные монтирования из
  `docker_volumes`: сам контейнер удаляется при каждой остановке.
* Игровой процесс работает от uid:gid пользователя игрового сервера (поле **«Имя пользователя на выделенном сервере»**).
  Этот пользователь должен существовать на ноде, хотя сервер работает в контейнере, иначе запуск завершится ошибкой
  `failed to lookup user`. Если поле пустое, используется пользователь самого демона.
* Порты публикуются на IP-адресе сервера: порт подключения по TCP и UDP, порт запросов по UDP и порт RCON по TCP, если
  они отличаются от порта подключения.
* Лимиты CPU и RAM берутся из [лимитов ресурсов](/ru/gameap_configure/game_servers.html#лимиты-ресурсов) сервера в
  панели (CPU в миллиядрах, RAM в байтах). Ключей метаданных для лимитов нет.
* Ни Docker, ни Podman не перезапускают контейнер самостоятельно: контейнер Docker создаётся с отключённой политикой
  перезапуска, а контейнер Podman — вообще без политики перезапуска (собственное значение по умолчанию в Podman — `no`).
  Упавший контейнер перезапускает демон в соответствии с настройкой сервера **«Автозапуск в случае падения»**.
* При остановке демон ждёт завершения процесса до 30 секунд, затем контейнер удаляется.
* В консоли показываются последние 500 строк лога контейнера. Команда из консоли доставляется по-разному: Docker
  подключается к stdin контейнера и записывает команду туда; Podman выполняет команду через `exec` внутри контейнера,
  поэтому до stdin игрового процесса она не доходит.

#### Установка в контейнере

Если заданы оба ключа — `docker_installation_image` и `docker_installation_script`, — установка выполняется в отдельном
контейнере:

1. скачивается установочный образ;
2. скрипт записывается в файл `.gameap_install.sh` в каталоге сервера (после установки файл удаляется);
3. создаётся временный контейнер `gameap-install-<XID>`, в который по пути `/mnt/server` смонтирован каталог сервера и
   переданы переменные окружения сервера;
4. скрипт выполняется интерпретатором из `docker_installation_entrypoint` (короткое имя вроде `ash` ищется в `/bin/`),
   иначе интерпретатором из shebang скрипта, иначе `/bin/sh`;
5. с Docker лог передаётся в реальном времени, с Podman — собирается после завершения контейнера;
6. после успешного выполнения владелец файлов меняется на пользователя сервера, контейнер удаляется.

Установка выполняется от `root`, если `docker_installation_user` не задан. Ненулевой код выхода означает ошибку
установки.

Контейнерный этап выполняется после обычной установки из репозиториев игры или Steam, если они у игры есть. Если у игры
нет ни правил установки, ни обоих контейнерных ключей, установка завершается ошибкой
`could not determine the rules for installing the game`. Если задан только один из двух ключей, контейнерный этап
пропускается, и демон лишь скачивает образ для запуска.

### Podman

Платформы: Linux, macOS.

Podman является альтернативой Docker, которая обеспечивает изоляцию игровых серверов в контейнерах. Он читает те же
[параметры контейнера](#параметры-контейнера), что и Docker (ключи сохраняют префикс `docker_`), и ведёт себя так же во
время работы, но подключается иначе: общается с REST API libpod (v4.0.0) через Unix-сокет, а из параметров подключения
использует только `socket_path` — `host`, `cert_path` и `api_version` игнорируются.

| Функционал                             |                                              |
|----------------------------------------|----------------------------------------------|
| Запуск, остановка, перезапуск серверов | ✅                                           |
| Перезапуск после сбоя                  | ✅ GameAP Daemon                             |
| Статистика                             | ✅                                           |
| Ограничение ресурсов (CPU / RAM)       | ✅                                           |
| Чтение консоли                         | ✅                                           |
| Отправка команд в консоль              | ⚠️ См. [Как это работает](#как-это-работает) |
| Изоляция                               | ✅                                           |

#### Конфигурация Podman

Должен быть запущен сокет Podman API. Rootless:

```bash
systemctl --user enable --now podman.socket
```

Root:

```bash
sudo systemctl enable --now podman.socket
```

##### Специфичные параметры

| Ключ в config | Описание                  | По умолчанию                                                                                                                                |
|---------------|---------------------------|---------------------------------------------------------------------------------------------------------------------------------------------|
| `socket_path` | Путь к Unix-сокету Podman | `unix:///run/user/<uid>/podman/podman.sock`, если демон работает не от root и этот сокет существует, иначе `unix:///run/podman/podman.sock` |

##### Примеры конфигурации

Rootless (по умолчанию):
```yaml
process_manager:
  name: podman
```

Rootful:
```yaml
process_manager:
  name: podman
  config:
    socket_path: "unix:///run/podman/podman.sock"
```

### Tmux

Платформы: Linux, macOS.

[Tmux](https://github.com/tmux/tmux) — это терминальный мультиплексор.
В настоящий момент является устаревшим менеджером процессов в GameAP,
который не рекомендуется к использованию, так как он не обеспечивает полной функциональности.

Tmux можно использовать на старых системах, а также внутри контейнеров (LXC, Docker/Podman и тд), виртуальных системах,
и системах в которых отсутствует Systemd и/или нет возможности использования Docker или Podman.

| Функционал                             |                             |
|----------------------------------------|-----------------------------|
| Запуск, остановка, перезапуск серверов | ✅                          |
| Перезапуск после сбоя                  | ✅ GameAP Daemon            |
| Статистика                             | ⚠️ Только запущен ли сервер |
| Ограничение ресурсов (CPU / RAM)       | ❌                          |
| Чтение консоли                         | ✅                          |
| Отправка команд в консоль              | ✅                          |
| Изоляция                               | ❌                          |

### Simple

Платформы: Linux, macOS, Windows. В панели отображается как **Простой (Управление скриптами)**.

У `simple` нет встроенного способа общаться с игровым сервером: он лишь выполняет команды из блока `scripts`
конфигурации демона, подставляя вместо `{command}` команду запуска, остановки или перезапуска сервера. Скрипты проверки
статуса и чтения консоли вызываются без команды сервера, поэтому с шаблоном по умолчанию `{command}` они разворачиваются
в пустую команду, и каждый такой вызов завершается ошибкой `empty command`. Без рабочего скрипта статуса состояние
сервера определить невозможно: он не отображается в панели и не перезапускается после сбоя.

В Linux демон переключается на `simple`, когда недоступны ни systemd, ни tmux.

| Функционал                             |                                        |
|----------------------------------------|----------------------------------------|
| Запуск, остановка, перезапуск серверов | ✅ Через настроенные скрипты           |
| Перезапуск после сбоя                  | ✅ GameAP Daemon, нужен скрипт статуса |
| Статистика                             | ⚠️ Только запущен ли сервер            |
| Ограничение ресурсов (CPU / RAM)       | ❌                                     |
| Чтение консоли                         | ⚠️ Нужен скрипт чтения консоли         |
| Отправка команд в консоль              | ⚠️ Нужен скрипт отправки команды       |
| Изоляция                               | ❌                                     |

#### Конфигурация Simple

```yaml
process_manager:
  name: simple
```

## Устранение неполадок

### Docker

**`failed to connect to docker daemon`** — демон не может подключиться к Docker. Проверьте, что Docker запущен
(`systemctl status docker`) и что пользователь, от которого работает демон, имеет доступ к `/var/run/docker.sock` —
обычно через членство в группе `docker` (`sudo usermod -aG docker <пользователь>`, затем войти в систему заново). При
удалённом Docker-демоне проверьте `host` и `cert_path`.

**`failed to lookup user <имя>`** — пользователь из поля **«Имя пользователя на выделенном сервере»** отсутствует на
ноде. Создайте пользователя в ОС или измените поле.

### Podman

**Ошибки подключения с упоминанием пути к сокету** — сокет Podman API не запущен или находится в другом месте.
Rootless:

```bash
systemctl --user enable --now podman.socket
ls -la /run/user/$(id -u)/podman/podman.sock
curl --unix-socket /run/user/$(id -u)/podman/podman.sock http://d/v4.0.0/libpod/info
```

Если демон работает от root, сокет находится по пути `/run/podman/podman.sock` (`sudo systemctl enable --now podman.socket`).
Если сокет расположен по нестандартному пути, задайте `socket_path`.

### Docker и Podman

**`could not determine the rules for installing the game`** при установке сервера из импортированного egg Pelican или
Pterodactyl — на ноде работает менеджер процессов, отличный от Docker и Podman. Смените менеджер в конфигурации демона
и перезапустите демон.
