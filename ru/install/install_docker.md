Панель распространяется готовым образом `gameap/gameap`. Демон в Docker не запускают: он должен
управлять процессами игровых серверов на выделенном сервере напрямую.

## Быстрый запуск

Самый простой вариант — SQLite, без отдельной базы данных:

```bash
docker run -d \
  --name gameap \
  -p 8025:8025 \
  -p 31718:31718 \
  -e DATABASE_DRIVER=sqlite \
  -e 'DATABASE_URL=file:/var/lib/gameap/db.sqlite?_busy_timeout=5000&_journal_mode=WAL&cache=shared' \
  -e AUTH_SECRET=$(openssl rand -base64 24) \
  -e ENCRYPTION_KEY=$(openssl rand -hex 32) \
  -e GRPC_EXTERNAL_HOST=panel.example.com \
  -v gameap-data:/var/lib/gameap \
  gameap/gameap:4.5
```

Панель откроется на `http://localhost:8025`. Логин и пароль первого администратора будут в журнале
контейнера:

```bash
docker logs gameap
```

> Два параметра из примера — обязательные, и оба легко упустить, потому что в готовых
> `docker-compose.yml` их нет. См. [Порт 31718](#порт-31718) и
> [Адрес панели для демонов](#адрес-панели-для-демонов).

## Порт 31718

По этому порту демоны подключаются к панели. В `Dockerfile` объявлен только `8025`, и в примере
`docker-compose.yml` из репозитория опубликован тоже только он.

**Порт 31718 нужно пробрасывать самостоятельно** — иначе панель будет работать, а ни один
выделенный сервер к ней не подключится.

```yaml
ports:
  - "8025:8025"
  - "31718:31718"
```

## Адрес панели для демонов

Панель подставляет свой адрес в команду установки демона. По умолчанию она берёт его из заголовка
запроса, а внутри контейнера это обычно `localhost` или имя сервиса — такая команда на удалённом
выделенном сервере работать не будет.

Задайте адрес, по которому панель доступна извне:

```yaml
environment:
  GRPC_EXTERNAL_HOST: panel.example.com
```

Если порт 31718 опубликован наружу под другим номером, укажите и его:

```yaml
environment:
  GRPC_EXTERNAL_PORT: 41718
```

> `GRPC_EXTERNAL_HOST` попадает в список имён самоподписанного сертификата gRPC. По возможности
> задайте переменную до первого старта. Если задать позже, достаточно перезапустить контейнер:
> панель обнаружит, что нужного имени в существующем сертификате нет, и перевыпустит его
> автоматически — удалять файлы вручную не нужно. Подробнее — [GRPC API](/ru/daemon/grpc.html).

## Теги образа

Каждый релиз публикуется под несколькими тегами:

| Тег                                             | На что указывает                              |
|-------------------------------------------------|-----------------------------------------------|
| `gameap/gameap:4.5.0`                           | Конкретный релиз                              |
| `gameap/gameap:4.5`                             | Последний патч-релиз линии 4.5                |
| `gameap/gameap:4`                               | Последний релиз линии 4.x                     |
| `gameap/gameap:latest`                          | Последний релиз                               |
| `gameap/gameap:sha-<sha>`, `gameap/gameap:main` | Сборки для разработки из ветки `main`         |

Миграции применяются автоматически при старте контейнера и необратимы, поэтому закрепите в
`docker-compose.yml` хотя бы минорную линию (`4.5`) и повышайте её осознанно, прочитав заметки к
новой версии на странице [Обновление](/ru/upgrade.html). `latest` и `main` в продакшене не
используйте.

## Docker Compose

Готовый файл `docker-compose.yml` есть в [репозитории панели](https://github.com/gameap/gameap).
Он поднимает панель вместе с PostgreSQL и Redis:

```bash
git clone https://github.com/gameap/gameap.git
cd gameap
docker compose up -d
```

К нему нужно добавить проброс порта 31718 и `GRPC_EXTERNAL_HOST`, как описано выше.

Пароли и ключи задаются через файл `.env` рядом с `docker-compose.yml`:

```dotenv
AUTH_SECRET=замените_на_32_случайных_байта
ENCRYPTION_KEY=замените_на_32_случайных_байта
POSTGRES_PASSWORD=замените_на_надёжный_пароль
LOGGER_LEVEL=info
```

> В примере `docker-compose.yml` значения `AUTH_SECRET` и `ENCRYPTION_KEY` по умолчанию —
> `change-me-in-production`. С такими ключами токены сессий подделываются тривиально.
> **Замените оба значения до первого `docker compose up`** — не после, а до.
>
> Позже сменить `ENCRYPTION_KEY` уже не получится безболезненно: сохранённые секреты TOTP станут
> нечитаемыми, и всем пользователям придётся подключать двухфакторную аутентификацию заново.
> См. [Безопасность](/ru/security.html).

Ключи обрабатываются по-разному: `AUTH_SECRET` приводится ровно к 32 байтам, а `ENCRYPTION_KEY`
хешируется целиком. Поэтому команды генерации в примере выше отличаются: `openssl rand -base64 24`
даёт ровно 32 символа, `openssl rand -hex 32` — 64.

## Данные и тома

Всё состояние панели хранится в `/var/lib/gameap`:

| Что                | Где                                                       |
|--------------------|------------------------------------------------------------|
| Файлы панели       | Каталог из `FILES_LOCAL_BASE_PATH`, в примере compose — `/var/lib/gameap/files` |
| Сертификаты gRPC   | Подкаталог `certs/` внутри него                            |
| Сертификаты ACME   | Подкаталог из `ACME_STORAGE_PATH`, по умолчанию `acme/`    |
| База данных SQLite | Там, где указано в `DATABASE_URL`                          |

Сертификаты и данные ACME хранятся не в корне тома, а **внутри каталога файлов панели**. При
настройках из примера `docker-compose.yml` полный путь к сертификату gRPC —
`/var/lib/gameap/files/certs/server/api-server.crt`.

Подключайте этот каталог томом, иначе при пересоздании контейнера потеряются сертификаты — и все
демоны перестанут подключаться.

Контейнер работает от непривилегированного пользователя `gameap`, поэтому у тома должны быть
подходящие права.

## Переменные окружения

Образ настраивается теми же переменными, что и обычная установка, — полный список в
[справочнике config.env](/ru/config.html). Файл `config.env` внутри контейнера не нужен.

Основные переменные:

| Переменная           | Назначение                                               |
|----------------------|----------------------------------------------------------|
| `DATABASE_DRIVER`    | `postgres`, `mysql` или `sqlite`                         |
| `DATABASE_URL`       | Строка подключения к базе                                |
| `AUTH_SECRET`        | Ключ подписи токенов, 32 случайных байта                 |
| `ENCRYPTION_KEY`     | Ключ шифрования секретов, 32 случайных байта             |
| `GRPC_EXTERNAL_HOST` | Адрес панели, по которому к ней подключаются демоны      |

Панели действительно нужны `DATABASE_URL` и `AUTH_SECRET`: у `AUTH_SECRET` значения по умолчанию
нет вовсе, а у `DATABASE_URL` есть только `file:/db.sqlite`, заданный в самом образе, — в корне
контейнера, вне подключённого тома. У `DATABASE_DRIVER` значение по умолчанию тоже есть (`sqlite`
в образе, `mysql` в панели), поэтому для любой другой базы его нужно задать — как в примере
compose с PostgreSQL. Задавайте все три явно.

`ENCRYPTION_KEY` формально не обязателен, но без него пароль подключения к демону хранится
открытым текстом, а плагины не могут хранить секреты: при
`PLUGINS_SECRETS_REQUIRE_ENCRYPTION=true` (по умолчанию) такие записи отклоняются, а при
`PLUGINS_SECRETS_REQUIRE_ENCRYPTION=false` секреты сохраняются в открытом виде — см.
[Безопасность](/ru/security.html). `GRPC_EXTERNAL_HOST` нужен, когда адрес, который
панель берёт из запроса, недоступен снаружи; внутри контейнера это обычный случай — см.
[Адрес панели для демонов](#адрес-панели-для-демонов).

Часто пригождаются и эти:

| Переменная             | По умолчанию | Назначение                                                                                                    |
|------------------------|--------------|---------------------------------------------------------------------------------------------------------------|
| `DEFAULT_LANGUAGE`     | `""`         | Язык интерфейса для пользователей, которые его не выбирали: `en`, `ru`, `es`, `de`. Пусто — по языку браузера |
| `UPDATE_CHECK_ENABLED` | `true`       | Проверка новых версий панели и демонов. Задайте `false` для установок без доступа в интернет                  |

Проверка обновлений обращается к адресам из `UPDATE_CHECK_URLS` и кеширует результат на
`UPDATE_CHECK_TTL` (по умолчанию `6h`).

Переменные плагинов начиная с 4.5.0 используют префикс `PLUGINS_*`. Если в старом compose-файле
заданы переменные `PLUGIN_*`, переименуйте их — см. [Обновление до 4.5.0](#обновление-до-450).

## За обратным прокси

Если HTTPS обслуживает nginx или Traefik, сертификаты в панели настраивать не нужно. Прокси должен
передавать заголовок `X-Forwarded-Proto: https` и **перезаписывать** его, а не дополнять.

Порт 31718 через обратный прокси обычно не проходит: демоны должны подключаться к панели напрямую.
Подробнее — [HTTPS и сертификаты](/ru/https.html).

## Обновление

Сначала сделайте резервную копию базы данных и тома с данными: миграции применяются при запуске
и необратимы.

Команда зависит от того, какая база используется. PostgreSQL из примера `docker-compose.yml`:

```bash
docker compose exec postgres pg_dump -U gameap gameap > gameap-backup.sql
```

MySQL или MariaDB в соседнем контейнере — с именем своего сервиса:

```bash
docker compose exec mysql mysqldump -u gameap -p gameap > gameap-backup.sql
```

Внешняя база копируется своими средствами, на том хосте, где она работает. База SQLite попадёт в
архив тома ниже, только если `DATABASE_URL` указывает внутрь тома, как в быстром запуске выше.
Со значением из образа, `file:/db.sqlite`, база лежит в корне контейнера и исчезнет вместе со
старым контейнером — сохраните её отдельно.

В томе лежат ещё и сертификаты gRPC, без которых демоны перестанут подключаться. Сначала остановите
контейнер, иначе журнал WAL оставит копии в несогласованном состоянии:

```bash
docker stop gameap

# Только если DATABASE_URL остался со значением из образа
docker cp gameap:/db.sqlite ./db.sqlite

docker run --rm -v gameap-data:/data -v "$PWD:/backup" alpine \
  tar czf /backup/gameap-data.tar.gz -C /data .
```

Лучше перенести такую базу в том: укажите в `DATABASE_URL` путь внутри тома, как в быстром запуске,
и положите файл туда. Тогда архив тома будет включать её сам.

Имя тома возьмите из своей конфигурации: `gameap-data` — в быстром запуске выше,
`gameap-storage` — в примере `docker-compose.yml`. Что ещё нужно сохранять и как восстанавливать,
описано на странице [База данных](/ru/database.html).

Затем укажите в `docker-compose.yml` новый тег образа — полагаться на `latest` не стоит, см.
[Теги образа](#теги-образа). После этого обновите контейнер:

```bash
docker compose pull
docker compose up -d
```

Общие заметки об обновлении — на странице [Обновление](/ru/upgrade.html).

### Обновление до 4.5.0

Внутри контейнера нет `gameapctl`, который переписал бы конфигурацию, поэтому изменения ниже
вносятся вручную в `docker-compose.yml` или `.env`.

**Переменные плагинов переименованы.** Каждая переменная `PLUGIN_*` стала `PLUGINS_*`, а
`PLUGINS_CACHE_ENABLED` / `PLUGINS_CACHE_DIR` — `PLUGINS_RUNTIME_CACHE_ENABLED` /
`PLUGINS_RUNTIME_CACHE_DIR`. Старые имена продолжают работать ещё один релиз и пишут в журнал
предупреждение об устаревании; если заданы и старое, и новое имя, действует новое. Переименуйте
их в любом случае — старые имена будут удалены в одном из следующих релизов.

Три переменные сменили ещё и формат значения, и для них совместимости **нет**: старые имена молча
игнорируются, и панель работает со значениями по умолчанию.

| Старое имя                        | Новое имя                  | Значение                                   |
|-----------------------------------|----------------------------|--------------------------------------------|
| `PLUGIN_HTTP_MAX_TIMEOUT_SECONDS` | `PLUGINS_HTTP_MAX_TIMEOUT` | Длительность с единицей: `30s`             |
| `PLUGIN_NET_MAX_TIMEOUT_SECONDS`  | `PLUGINS_NET_MAX_TIMEOUT`  | Длительность с единицей: `10s`             |
| `PLUGIN_NET_READ_BUFFER_BYTES`    | `PLUGINS_NET_READ_BUFFER`  | Размер — число байт или с суффиксом: `64K` |

Полный список переменных — в [справочнике config.env](/ru/config.html).

**Логины и адреса почты приводятся к нижнему регистру.** При первом запуске 4.5.0 миграция
переводит все сохранённые логины и адреса в нижний регистр; пользователи, входившие с заглавными
буквами, входят как прежде — панель приводит введённое в форме входа к нижнему регистру. Если
после приведения два аккаунта совпали, идентификатор сохраняется только за одним из них, а в
журнале панели указываются id обоих — поля `user_id` и `kept_by_user_id`; сами логины и адреса
в журнал не попадают. См. [Обновление](/ru/upgrade.html).
